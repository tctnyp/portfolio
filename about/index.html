About Me

Tan Chee Tiong

Aspiring developer — server hosting, programming, and Minecraft development. Below is the long version of how I got here.

Start here

Hey, everyone. I'm Tan Chee Tiong, and I build and run things that other people rely on: servers, bots, and the infrastructure that keeps them online. If you only read one line of this page, make it this one — almost everything I know started because something in front of me was broken, slow, or locked down, and I refused to leave it alone.

I've written this as a story rather than a list of skills, because the list on its own wouldn't make much sense. “Runs Minecraft networks” sounds random until you know it began with a school laptop I wasn't supposed to modify. The path from there to here was messy, and the messy part is the part worth reading.

2022 — The Chromebook that started everything

In Secondary 1 the school gave us Chromebooks to use for our studies. On paper it was a good idea. In practice mine was slow, heavily managed, and restricted in ways that felt completely arbitrary. It would block the most random sites for no reason at all — documentation pages, reference material, things I actually needed for schoolwork. That got annoying very quickly, so I started looking for a way around it.

The internet, predictably, had opinions. The first method I tried was repeatedly disabling the management extension with scripts. The second was corrupting the extension's installation so it couldn't load at all. Both worked for a while, and both were temporary. The extension would eventually repair itself, sync back down from the management server, and quietly undo everything overnight.

What I didn't realise at the time is that the failures were the useful part. To get any of it working I had to understand what a browser extension actually is, how enterprise enrollment pushes policy down to a device, why a managed machine phones home, and what “managed” really means when somebody else holds the keys. I wasn't studying any of that. I was just trying to open a website. I learned it anyway.

Somewhere in that rabbit hole I found a way to permanently unenroll the device. I sat on it for months. I knew it would work, and I knew exactly what would happen if it went wrong, so I did nothing about it for a whole year.

2023 — The unenrollment

Eventually I stopped hesitating and went through with it. Unenrolling meant getting into developer mode, wiping the machine, and rebuilding it from scratch — which also meant that if I made a mistake I'd be handing in a very expensive brick and explaining why. It worked. The bigger surprise was how much I'd picked up just getting to that point.

It was the first time a computer felt like mine rather than something I was borrowing. Once I could install whatever I wanted, I stopped consuming and started building. I poked at Linux, I broke the install, I reinstalled it, and then I broke it again in a more interesting way. I got comfortable in the terminal purely because there was no button for the thing I wanted to do.

This is also the year I stopped being afraid of the sentence “I don't know how that works.” Before, that ended the conversation. After, it became a starting point. Not knowing something stopped feeling like a wall and started feeling like a to-do item.

2024 — Renting my first real server

In Secondary 3 I went from breaking my own machine to renting someone else's. I wanted to run a Minecraft server for friends and assumed it would take an evening. It did not. It turned into a crash course in everything I now do daily: SSH, Linux administration, hosting panels, port forwarding, firewalls, Java memory flags, plugin conflicts, and the very specific misery of a server that runs perfectly right up until eight people join it.

Hosting is where my mindset genuinely changed. Writing code that works once is easy. Keeping something online while real people are using it is a completely different discipline. Suddenly I cared about uptime, backups, restart schedules, tick lag, and what happens at 2am when nobody is awake to fix it. The important question stopped being “does it work?” and became “what happens when it doesn't?”

I also learned that players are the most thorough QA team you will ever have. They will find the one duplication bug, the one command missing a permission check, and the one corner of the map that crashes the server — usually within the hour, and always while I was supposed to be doing homework.

2025 — Building for other people

Secondary 4 was the year my projects stopped being just for me. I became co-owner of Hyper Studios, a Minecraft network running on both Java Edition and Eaglercraft with game modes like BedWars, SkyBlock, Survival and Duels. Being responsible for a community instead of a hobby server changes the job entirely — you're dealing with staff, moderation, player expectations, and infrastructure decisions that are painful to reverse later.

Around the same time I got frustrated with Discord bots. Every server ends up inviting five of them: one for music, one for moderation, one for tickets, one for invite tracking. Half the useful features sit behind a paywall, and none of them talk to each other. It felt backwards, so I built HyperXUtility — a single bot covering what those five were doing, because I was convinced one good bot should be enough.

I also spent time with Zenix.SG on the support side, which taught me the part of this field nobody posts about: talking to users. Diagnosing a problem from a vague message, explaining a fix without being condescending, and admitting when something is genuinely our fault. Support work made me a noticeably better developer, mostly because it forces you to see your own systems through somebody else's eyes.

All of this happened alongside O-Levels, which was exactly as balanced as it sounds. If nothing else, that year taught me how to prioritise ruthlessly and how to tell my own ideas “not this week.”

Now — Where I'm heading

I'm studying at Nanyang Polytechnic now, and the question has shifted from “can I make this work?” to “is this actually good?” Design, usability, and the experience of the person on the other side of the screen used to feel like optional polish to me. They don't anymore. A fast server behind a confusing interface is still a bad product.

These days I care about reliability over cleverness, because boring predictable systems beat impressive ones that fall over. I care about writing code I can still read in six months, since if future me can't follow it then it isn't finished. I try to keep the number of moving parts low, because every dependency is something I'll eventually have to debug at a bad time. And above all I try to actually ship, because a rough thing that exists beats a perfect thing that doesn't.

Longer term I want to keep working where programming, hosting and community overlap — building infrastructure that's technical underneath and calm to use on top. Fewer half-finished experiments, more things people actually depend on. That's the story so far, and if any of it sounds like your kind of thing, the contact page is one click away.
